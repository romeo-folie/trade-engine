# Task: Execution router

## Description

Wire the pieces together at the signal seam. Intercept the ORB `BracketParams` at its single placement point; for options-mode underlyings, run the gate engine, size by premium, place a limit-at-mid entry, and persist the trade with full contract identity. Non-options underlyings fall through to the existing bracket path with zero change.

## Acceptance Criteria
- [ ] At the placement site (`internal/orb/scheduler.go:1205-1360`), when the underlying is options-mode, route `BracketParams` to the options path; otherwise call the existing `PlaceBracket`/`PlaceMarketBracket` unchanged.
- [ ] Options path: run Task 3 gates → on any abort, log the reason and place nothing (no trade recorded, no partial state).
- [ ] On pass: resolve OCC contract (Task 2), size `contracts = floor(premium_budget / (mid × 100))`, capped so max loss (premium × contracts × 100) ≤ configured per-trade risk.
- [ ] Entry = limit order at computed mid. If unfilled within the configured window, reprice or cancel per policy — never leave a silently dangling working order.
- [ ] Persist the `orb_trades` row via `store.CreateORBTrade` with `asset_class='option'`, full contract identity, multiplier, and the underlying's stop/target levels (needed by Task 6 exits).
- [ ] Zero-regression test: a non-options underlying produces byte-identical placement to today.
- [ ] Tests: gate-abort → no order; gate-pass → correct OCC order + persisted identity; sizing/cap math.

## Technical Details
- Interception: `placeAndRecord`/breakout-confirm block (`scheduler.go:1206-1271`, equities single-bracket path :1329-1360).
- Signal struct consumed: `BracketParams` (`internal/orb/executor.go:22-30`) — carries underlying, side, entry-stop, stop, target, risk-sized qty (share qty is replaced by premium-based contract qty here).
- The underlying stop/target from `BracketParams` are stored on the option trade row so exits (Task 6) can watch the underlying against them.
- Fill/reprice policy shared conceptually with any limit execution; keep it a small, testable helper.

## Dependencies
- Task 1 (identity), Task 2 (order path + contract resolution), Task 3 (gates). Task 4 feeds Task 3's IV-Rank gate.
