# Task: JMIA verification + collapse migration

## Description

Eight stale JMIA `trades` rows from local dev-mode restarts are silently consuming the position budget. Only one row (Mar 31, `b47400e5-…`) has a linked `orders` row; the other seven were never observed by the broker. Verify against the live broker, then collapse the eight rows into one canonical trade row.

This task is sequential and blocking: it produces the schema additions the rest of Epic A relies on (the `consolidated` enum value and `consolidated_into` column).

## Acceptance Criteria

- [ ] Broker quantity for JMIA confirmed; recorded in PR description.
- [ ] New migration applies cleanly: adds `consolidated` to `trade_status` enum, adds `consolidated_into UUID NULL REFERENCES trades(id)` to `trades`, adds index `idx_trades_consolidated_into`.
- [ ] Data migration collapses 8 → 1: canonical row's `quantity` and `entry_price` reflect the broker-reported aggregate; the other 7 have `status='consolidated'` and `consolidated_into` set to the canonical row's id.
- [ ] All 7 consolidated rows preserve their original `quantity`, `entry_price`, `signal_id`, `opened_at` — only `status` and `consolidated_into` change.
- [ ] `GetOpenTrades` (and any other queries that list open trades) excludes `status='consolidated'`.
- [ ] Smoke test: after migration, `SELECT count(*) FROM trades WHERE ticker='JMIA' AND status='open'` returns 1.
- [ ] Reversibility documented in PR description: `UPDATE trades SET status='open', consolidated_into=NULL WHERE consolidated_into=$canonical_id`.

## Technical Details

- Migration directory: same one consumed by `store.Migrate` (next sequential filename).
- Two-statement migration:
  1. `ALTER TYPE trade_status ADD VALUE IF NOT EXISTS 'consolidated';`
  2. `ALTER TABLE trades ADD COLUMN IF NOT EXISTS consolidated_into UUID REFERENCES trades(id);`
  3. `CREATE INDEX IF NOT EXISTS idx_trades_consolidated_into ON trades(consolidated_into);`
- Data migration: separate migration file or one-shot script invoked once. Wraps the 8-row update in a single transaction. Selects canonical row deterministically: `SELECT id FROM trades WHERE ticker='JMIA' AND status='open' AND id IN (SELECT trade_id FROM orders WHERE ticker='JMIA') ORDER BY opened_at LIMIT 1` — i.e. the only one with a broker-linked order.
- Broker verification step: a small standalone script or psql query that reports broker JMIA quantity. Must be run and recorded before the data migration is applied.
- Search and update queries that filter open trades — confirm `WHERE status='open'` is the predicate, and that `'consolidated'` is naturally excluded.
